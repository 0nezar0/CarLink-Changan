- الإصدار: `versionName` = `CS75 Plus 2023 v1.6.1`، واللاحقة `-barhide-test`، و`versionCode` = **10037** (أكبر من v1.6 الذي رقمه 10036 حتى يثبّت فوقه).

## 1. إدخال سيارة جديد في قائمة الماركات

لم نُعد تسمية خيار **شانجان** العام. أُضيف إدخال جديد مستقل:

| الحقل | القيمة |
|---|---|
| الثابت في الكود | `CarBrand.CHANGAN_CS75_PLUS` |
| الاسم بالعربي | **شانجان /CS75 Plus 2023-2022 فقط** |
| الاسم بالإنجليزي | **Changan / CS75 Plus 2022-2023 only** |
| مورد النص | `carlink_settings_car_brand_cs75` |

يظهر هذا الإدخال **أولاً** في قائمة اختيار السيارة، ثم يأتي خيار شانجان العام (`CarBrand.CHANGAN`) بعده كأي ماركة أخرى.

كل السلوك الخاص بشاشة CS75 أصبح مربوطاً بـ `isChanganCs75Plus` فقط:

- الهامش العلوي (top margin) بقيمة 48 بكسل.
- شعار شانجان في زر الرجوع للسيارة في CarPlay وفي الإعدادات › السيارة.
- حد 30 fps في وضع الصورة Automatic.
- قسم إخفاء شريط الحالة (انظر أدناه).
- القيم الافتراضية الجديدة لـ CarPlay وAndroid Auto (mm400، HEVC، DPI 200).

الملف الأساسي: `carlink-core/src/main/java/com/carlink/core/settings/CarBrand.kt`.

## 2. شانجان العامة ترجع للسلوك الافتراضي، مع ترحيل (migration) مرة واحدة

خيار **شانجان** العام (`CarBrand.CHANGAN`) لم يعد يفعّل أي تخصيص لـ CS75: لا هامش علوي، ولا إخفاء شريط الحالة، ولا شعار خاص، ولا حد الـ 30 fps، ولا القيم الافتراضية mm400 / HEVC / DPI 200. يتصرّف مثل تويوتا أو هيونداي أو أي ماركة أخرى.

### الترحيل مرة واحدة

المستخدمون الذين كانت ماركتهم المحفوظة هي شانجان العامة (قبل هذا التقسيم) يجب ألا يخسروا إعدادات CS75. لذلك:

- عند أول قراءة بعد التحديث، الدالة `CarBrandStore.migrateChanganToCs75Once()` تنقل القيمة المحفوظة من `CHANGAN` إلى `CHANGAN_CS75_PLUS`.
- يُحفظ علم `car_brand_cs75_migrated` (`CarBrandStore.KEY_CS75_MIGRATED`) في تفضيلات `carlink_vehicle`.
- بعد تثبيت العلم، اختيار لاحق لـ شانجان العامة يُترك كما هو (لا يُرحَّل مرة ثانية).
- إذا لم تكن هناك ماركة محفوظة، أو كانت ماركة أخرى، لا يُنقل شيء إلى CS75؛ يُثبت العلم حتى لا تُعاد المحاولة.

عند هذا الترحيل تُطبَّق أيضاً القيم الافتراضية لـ CarPlay/Android Auto (القسم 7)، إن لم يكن المستخدم قد عيّنها بنفسه.

## 3. تصنيف CS75 في قائمة الإعدادات

إعدادات CS75 تظهر كـ **تصنيف (category) في قائمة الإعدادات اليسرى**، في **أول موضع فوق «الاتصال»**، وبنفس أسلوب التصنيفات الأخرى. المحتوى يُعرض في الجزء الأيمن القابل للتمرير (أو بعد الدخول للتصنيف في التخطيط الضيّق)، مثل بقية الإعدادات. لا توجد بطاقة ثابتة بعرض الشاشة أعلى التخطيط.

يظهر التصنيف فقط عندما تكون الماركة المختارة هي الإدخال `CHANGAN_CS75_PLUS`.

عنوان التصنيف يجب أن يكون بالضبط (مع عزل Unicode للنص اللاتيني حتى لا ينعكس الترتيب في RTL):

> **اعدادات خاصة لشانجان /CS75 Plus 2023-2022 فقط**

بالإنجليزية تقريباً: «Changan / CS75 Plus 2022-2023 only settings». الجزء اللاتيني `CS75 Plus 2023-2022` ملفوف بـ FSI/PDI (`U+2068` … `U+2069`) في العنوان، وفي اسم الخيار بقائمة السيارات، وفي سؤال أول تشغيل.

داخل التصنيف:

- أوضاع إخفاء شريط الحالة (إيقاف / الكل ما عدا الشاشة الرئيسية / تطبيقات مختارة).
- تنبيه إذن إمكانية الوصول (Accessibility) وزر فتح الإعدادات وحالة التفعيل.
- منتقي التطبيقات عند اختيار الوضع الثاني.
- مفتاح الهامش العلوي (48 بكسل).

الملفات: `SettingsChangan.kt`، `SettingsScreen.kt`، `SettingsPages.kt`، و`SettingsCategory.CHANGAN_CS75`.

## 4. أوضاع إخفاء شريط الحالة ومنتقي التطبيقات

بدل مفتاح واحد، هناك ثلاثة خيارات متنافية (`HideCarStatusBarMode`):

| الوضع | الثابت | المعنى |
|---|---|---|
| إيقاف | `OFF` | لا يُرسل طلب إخفاء. هذا هو الافتراضي. |
| الإخفاء في كل التطبيقات ما عدا الشاشة الرئيسية | `ALL_EXCEPT_LAUNCHER` | يُخفى الشريط في أي تطبيق ما عدا الشاشات الرئيسية المعروفة للسيارة. |
| تطبيقات مختارة | `SELECTED_APPS` | يُخفى الشريط فقط في التطبيقات التي يعلّمها المستخدم بعلامة ✔، بالإضافة إلى CarLink/الإسقاط. |

حزم الشاشة الرئيسية المستثناة في الوضع الأول:

- `com.faurecia.app.in`
- `com.incall.apps.in`

في **كلا** الوضعين التشغيليين (ليس الإيقاف): شريط الحالة يُخفى دائماً أثناء CarLink نفسه وأثناء الإسقاط (CarPlay / Android Auto)، حتى لو لم يكن التطبيق في قائمة الاختيار.

منتقي التطبيقات يعرض التطبيقات القابلة للتشغيل (launchable) مع مربعات اختيار. الاختيار يُحفظ في `hideCarStatusBarPackages`. المفتاح المشتق `hideCarStatusBar` يكون true عندما الوضع ≠ `OFF`.

الملفات:

- `carlink-core/src/main/java/com/carlink/core/settings/HideCarStatusBarMode.kt`
- `carlink-core/src/main/java/com/carlink/core/settings/UnifiedSettings.kt`
- `app/src/main/java/com/carlink/app/switcher/FceSystemBar.kt`
- واجهة المنتقي في `SettingsChangan.kt`

## 5. تنبيه إذن إمكانية الوصول (Accessibility)

إخفاء الشريط حسب التطبيق المفتوح يحتاج خدمة إمكانية الوصول، لأنها الطريقة المتاحة لمعرفة النافذة الأمامية على هذه الشاشة. النص الظاهر في الإعدادات يجب أن يكون بالضبط:

> **تنبيه: لازم تفعّل إذن إمكانية الوصول لـ CarLink عشان يعرف التطبيق المفتوح ويخفي شريط الإشعارات.**

معه:

- زر يفتح إعدادات إمكانية الوصول في النظام (`Settings.ACTION_ACCESSIBILITY_SETTINGS`).
- حالة واضحة: مفعّل أو غير مفعّل.

تعريف الخدمة: `app/src/main/res/xml/carlink_fce_accessibility.xml`، والخدمة `FceBarAccessibilityService` مسجّلة في `AndroidManifest.xml` مع `<queries>` لحزم الشاشة الرئيسية.

الخدمة تستمع إلى `TYPE_WINDOW_STATE_CHANGED` (نفس أسلوب Bar Hider 2.0)، ثم تعيد إرسال أمر الإخفاء. تتجاهل لوحة المفاتيح (IME) ونظام الواجهة `systemui` و`fcesystemui`، لكنها **لا** تتجاهل حزمة CarLink نفسه (حتى يبقى الشريط مخفياً وهو في الواجهة). بعد كل تغيّر تُعاد المحاولة بعد 500 ms لأن نظام السيارة قد يعيد إظهار الشريط.

## 6. آلية البثوث (broadcasts) في FceSystemUI

شاشة CS75 Plus تستخدم واجهة نظام اسمها **FceSystemUI**. إخفاء شريط الحالة ليس API عاماً لأندرويد، بل بث ضمني (implicit broadcast):

| الفعل (Intent action) | المعنى |
|---|---|
| `com_fce_system_statusbar_hide` | اطلب إخفاء شريط الحالة |
| `com_fce_system_statusbar_show` | اطلب إظهار شريط الحالة |

الوسم في السجلات (log tag): **`CarLinkFceBar`**.

**لماذا «لا يعمل» أحياناً بعد أول تجربة:** FceSystemUI يعيد إظهار الشريط من تلقاء نفسه إذا لم تكن الحزمة الأمامية في قائمته البيضاء (whitelist). القائمة المعروفة تضم تطبيقات مثل amap وeasyconn وkuwo وvlink وxiaoma وiflytek و`tv.newtv.vcar`. حزمة CarLink (`com.carlink.app.hudtest`) **ليست** ضمنها. لذلك إرسال أمر الإخفاء مرة واحدة عند بدء الإسقاط غير كافٍ.

ما يفعله هذا البناء:

- يرسل الإخفاء فوراً عند تفعيل الإعداد، وليس فقط أثناء الإسقاط.
- يعيد الإرسال دورياً / عند الرجوع للتطبيق (resume) وعبر مؤقت 500 ms.
- يعيد الإرسال عند كل تغيّر نافذة عبر خدمة Accessibility.
- يربط الحالة بواجهة الإسقاط عبر `SwitcherController.install()` و`ProjectionVisibility.front.collect`.

الكود: `app/src/main/java/com/carlink/app/switcher/FceSystemBar.kt` و`FceBarAccessibilityService.kt` و`SwitcherController.kt`.

هذه الميزة منسوخة فكرتها من تطبيق Bar Hider، لكنها مُنفَّذة داخل CarLink؛ لا يُدمج مستودع Bar Hider ولا PR #4.

## 7. القيم الافتراضية الخاصة بـ CS75 (mm400، HEVC، Android Auto 200، الهامش)

تُطبَّق **فقط** عند اختيار `CHANGAN_CS75_PLUS`، وكذلك مرة واحدة عند ترحيل شانجان العامة إلى هذا الإدخال. لا تُفرض على الماركات الأخرى ولا على شانجان العامة. إذا كان المستخدم قد عيّن القيمة بنفسه في الإعدادات المتقدمة (Advanced)، لا تُستبدل.

التنفيذ: `carlink-core/src/main/java/com/carlink/core/settings/Cs75ProjectionDefaults.kt`، يُستدعى من `CarBrandStore.set()` و`chosen()` (بعد الترحيل). علم منع التكرار: `cs75_projection_defaults_applied` في تفضيلات `carlink_vehicle`.

### 7.1 عرض CarPlay «mm400»

- إعداد Advanced: **`cp_width`**
- العنوان: Screen width reported to iPhone
- الخيار: **400 mm** (أصغر خيار بالمليمتر)
- مفتاح الحفظ: `display_width_physical_mm` في تفضيلات `xcertplay_airplay`
- الدوال: `AirPlayPersistence.load/saveWidthPhysicalMm`

هذا ليس هامشاً ولا دقة شاشة؛ هو العرض الفيزيائي الذي يُبلَّغ لجهاز الآيفون حتى يحسب حجم واجهة CarPlay.

حتى لا تعيد الجلسة الكتابة فوق 400 mm من إعداد «حجم الواجهة» (Interface size، القيمة الافتراضية Medium = 180 mm)، يُضبط Interface size على **`CUSTOM`** عند تطبيق هذا الافتراضي، ما لم يكن المستخدم قد اختار Custom مسبقاً ويملك عرضاً مخزَّناً (حينها يُترك عرضه). `CarPlaySettingsPolicy.apply()` أيضاً لا يستبدل عرضاً مخزَّناً لماركة CS75.

### 7.2 CarPlay HEVC

- إعداد Advanced: **`cp_hevc`**
- العنوان: Efficient video (HEVC)
- مفتاح الحفظ: `hevc_enabled` في `xcertplay_airplay`
- الافتراضي السابق في المحرّك: `hevcDefault = false`
- على CS75: إذا لم يكن المفتاح موجوداً، يُحفظ **true**

إذا كان المفتاح موجوداً مسبقاً (المستخدم أو سياسة سابقة كتبته)، لا يُغيَّر عند التطبيق الأول. أثناء الجلسات، وضع الصورة Automatic قد يحاول إعادة كتابة HEVC؛ للكود حراسة حتى لا يُشغَّل من جديد إذا كان المستخدم قد أطفأه، مع السماح بإيقافه إذا فشلت المحاولة (تفادي شاشة سوداء عبر مسار CarPlayHevcMemory / PicturePolicy).

### 7.3 Android Auto «200»

- إعداد Advanced: **`aa_dpi`**
- العنوان: Pixel density (DPI)
- الخيار: **200**
- مفتاح المحرّك: `dpi-pixel-density`
- الافتراضي السابق: **0** (Automatic)

هذا إعداد كثافة بكسل (DPI) لواجهة Android Auto، وليس دقة فيديو ولا هامش. يُكتب عبر `AndroidAutoSettings.write`. إذا لم يكن Interface size على `CUSTOM`، تضع جلسة Android Auto القيمة `0` في كل اتصال (`AaSessionSettings`)؛ لذلك يُضبط الحجم على Custom عند تطبيق افتراضي 200، ما لم يكن المستخدم قد عيّن كثافة بنفسه تحت Custom.

### 7.4 الهامش العلوي (margin)

هذا ليس الإعداد «200». الهامش الموجود مسبقاً لشاشة CS75 هو **48 بكسل أعلى الشاشة** (`ScreenMargins.CHANGAN`: top = 48، وباقي الحواف 0) حتى لا يختفي جزء من CarPlay أو Android Auto أو واجهة CarLink تحت شريط حالة السيارة.

- يظهر مفتاحه في قسم CS75 أعلى الإعدادات.
- يُطبَّق فقط عندما الماركة هي `CHANGAN_CS75_PLUS` عبر `UnifiedSettings.marginsFor`.
- شانجان العامة لا تحصل على هذا الهامش.
- من **v1.6.5** الافتراضي **إيقاف**. اختيار السيارة أو نعم في سؤال أول تشغيل لا يشغّله. من كان عنده التشغيل فقط لأن سؤال أول تشغيل السابق كان يفعّله مع إخفاء الشريط، يُطفأ مرة واحدة بترحيل `cs75_top_margin_off_v10041` (versionCode 10041). إن كان المستخدم قد شغّل الهامش وحده (والإخفاء ما زال موقوفاً) أو اختار وضع إخفاء مخصص، يبقى كما هو.

## 8. التحديث التجريبي ومسار الـ prerelease

خيار «الحصول على نسخ تجريبية» **كان موجوداً مسبقاً** في الإعدادات › حول (`carlink_about_test_versions` = **الحصول على نسخ تجريبية**). لم يُضف مفتاح جديد. الافتراضي: **إيقاف**.

سلوك المحدّث داخل التطبيق:

- إذا الخيار **إيقاف**: يقرأ `releases/latest` فقط، و`parse(allowPrerelease=false)`. لن تُعرض هذه النسخة التجريبية ما دام Latest هو v1.6.
- إذا الخيار **تشغيل**: يقرأ قائمة الإصدارات (`LIST_URL`) ويأخذ الأحدث مع `allowPrerelease=true`.
- المسودات (drafts) **لا تُعرض أبداً**.
- الوسم (tag) يجب أن يكون بالشكل `vX.Y` أو `vX.Y.Z`. وسم مثل `v1.6-barhide-test` يُرفض كـ `MALFORMED_TAG`. لذلك وسم هذه التجربة هو **`v1.6.1`**.
- اسم ملف الـ APK: `CarLink-CS75Plus2023-v1.6.1.apk` ومعه `CarLink-CS75Plus2023-v1.6.1.apk.sha256`.
- المستودع الذي يقرأه المحدّث: **`0nezar0/carlink-releases`** (عام). المستودع الخاص لا يُستخدم مصدراً للتحديث داخل التطبيق.
- الفحص قبل التثبيت (`UpdateVerifier`): `versionCode` أعلى، نفس الحزمة `com.carlink.app.hudtest`، نفس بصمة التوقيع المثبتة، ومطابقة checksum.

نص «ما الجديد» داخل التطبيق (الجديد / What’s new) يأتي من جسم إصدار GitHub **فوق** السطر `<!-- more -->`، ويُغذَّى من `CHANGELOG.md` وملاحظات الإصدار العربية. صف الجدول في `README.md` تحت عنوان «## الجديد» يلخّص الأمر للمستخدم.

### سياسة نشر هذه التجربة

- تُنشر على `0nezar0/carlink-releases` كـ **prerelease** (ليست draft، وليست Latest).
- الأمر المعتمد: `--prerelease --latest=false`.
- Latest يجب أن يبقى **v1.6**.
- أي مسودة قديمة بوسم `v1.6-barhide-test` تُستبدل أو تُحذف، ولا تُستخدم.
- ملفات CarPlay الخاصة (MFi) موجودة في هذا البناء؛ لذلك لا يُنشر الإصدار كـ Latest للعامة بالخطأ.

## 11. كيف تُبنى النسخة وكيف تُنشر

اعمل دائماً على فرع `feature/changan-fce-bar-hide` في المستودع **الخاص**. لا تدمج طلبات السحب ما لم يُطلب ذلك صراحة. هذا الملف يُرفع إلى المستودع الخاص فقط، وليس إلى `carlink-releases`.

1. ادفع الالتزامات إلى `feature/changan-fce-bar-hide`.
2. من GitHub: **Actions › Build CarLink › Run workflow**.
3. اختر `build_type = release` والفرع `feature/changan-fce-bar-hide`.
4. الـ workflow:
   - يستخدم السرّ `CARLINK_DEBUG_KEYSTORE_B64` لتوقيع الـ APK بنفس مفتاح التطبيق المثبّت.

   - يتحقق أن ملفات CarPlay (`assets/offline-mfi/certificate.p7b` و`identity.pk8`) داخل الـ APK.

5. نزّل الـ APK، وأعد تسميته عند النشر إلى `CarLink-CS75Plus2023-v1.6.1.apk`، وأولِد ملف `.sha256` بجانبه.

## 12. إصلاح: CarPlay يصل لآخر خطوة بدون صورة على نقطة اتصال السيارة

هذه المشكلة موجودة في **v1.6 المستقر** (ليست من إعدادات mm400 / HEVC / DPI 200 في هذا الفرع). الأعراض: الآيفون يتصل بنقطة اتصال السيارة (car hotspot)، وCarPlay يتقدّم حتى آخر مرحلة (الصورة / Picture) ثم يتوقف ولا تظهر الشاشة. **Android Auto على نفس نقطة الاتصال يعمل**.

المقارنة:

- Android Auto يختار واجهة الـ AP ويربط جلسته على عنوان IPv4 الخاص بها (`SoftApNetworkPolicy` في `vendor/diauto`).
- مسار CarPlay للتحكم (RTSP على المنفذ 7000) يربط كل عائلة عناوين صراحة عبر `AirPlayPortSelector` («specific per-family listeners avoid relying on a platform's IPV6_V6ONLY default»). نفق iAP أيضاً يُربط على `session.localAddress`. لذلك الاقتران وSETUP يكتملان.
- منافذ **الصورة والتوقيت (NTP) والأحداث وkeep-alive والصوت RTP** كانت تُربط فقط على `::` (IPv6 wildcard) في:
  - `ScreenStream.kt` (TCP لاستقبال الشاشة)
  - `NtpClock.kt` و`AirPlaySession.openKeepAlive` (UDP)
  - `AirPlaySession.openEvent`
  - `AudioStream.bindAnyPort`
- على أندرويد، مقبس `::` يكون IPv6 فقط (`IPV6_V6ONLY`). نقطة اتصال السيارة عادة IPv4 (مثل 192.168.43.1). الآيفون يفتح منفذ الصورة على نفس عنوان IPv4 لجلسة التحكم، والقبول لا يحدث، فتتجمّد مرحلة الصورة. الشبكة المشتركة (same Wi-Fi) قد تعمل إذا استخدمت IPv6 link-local.

الإصلاح (via `// CarLink` hooks): هذه المنافذ تُربط الآن على عنوان جلسة التحكم نفسه (`airPlayMediaBindAddress` / `session.localAddress`)، مثل نفق iAP.

ملف المساعد: `vendor/diplay/shared/src/main/java/com/shilapi/xcertplay/airplay/AirPlayMediaBind.kt`.

الأزرار: **نعم** / **لا**.

## 16. إصلاح: CarPlay يتوقف عند «الربط» على نقطة اتصال السيارة (v1.6.3)

على v1.6.2 (وبعد إصلاح صورة CarPlay في v1.6.1) ما زال مسار **نقطة اتصال السيارة** يفشل عند مرحلة «الربط»: البلوتوث ينجح («الوصول إلى الجوال» و«الجوال رد»)، والآيفون يستلم بيانات الواي فاي عبر iAP2، ثم لا يفتح اتصال AirPlay TCP («لم يفتح الـ iPhone خدمة CarPlay عبر Wi-Fi»). **نفس الآيفون على الشبكة المشتركة يعمل**. هذه المشكلة موجودة أيضاً في مسار v1.6 المستقر؛ ليست من إعدادات CS75.

السبب الأرجح: بعد تشغيل نقطة الاتصال كان المسار يختلف عن الشبكة المشتركة. كان يعلن عنوان MAC الخاص بنقطة الاتصال كهوية جهاز AirPlay (بينما الشبكة المشتركة تستخدم الهوية المحفوظة)، وقد ينشر عائلة IPv6 إذا كانت محفوظة من جلسة شبكة مشتركة سابقة، رغم أن نقطة اتصال السيارة عادة IPv4.

الإصلاح (عبر خطاف `// CarLink` فقط): بعدما تصبح نقطة الاتصال جاهزة، يُرفع واجهة الـ AP ثم يُربط عليها بنفس مسار الشبكة المشتركة (`ExistingWifiManager` مع `preferredInterface`): نفس قائمة العناوين، ونفس Bonjour/mDNS، ونفس المستمعات، ونفس هوية AirPlay المحفوظة. مسار نقطة الاتصال ينشر IPv4 أولاً دائماً. ملف المساعد: `vendor/diplay/shared/src/main/java/com/shilapi/xcertplay/network/CarHotspotSharedLanManager.kt`.

## 17. إصلاح: تعارض IPv6 على نقطة اتصال السيارة (v1.6.4)

المستخدم بلّغ أن عنوان IPv6 هو سبب المشكلة («يسوي تعارض»). حتى بعد v1.6.3، مسار نقطة الاتصال كان قد يعلن عنوان IPv6 link-local على نفس الواجهة (Bonjour AAAA، ومستمعات إضافية، و0x4301)، فيتعارض مع IPv4.

من v1.6.4 صار مسار نقطة اتصال السيارة **IPv4 فقط**:
- Bonjour يعلن سجلات A فقط (بدون AAAA أو IPv6 link-local).
- كل مستمعات AirPlay (التحكم RTSP، والحدث، وNTP، وkeep-alive، والصورة والصوت) تُربط على عنوان IPv4 لنقطة الاتصال، وليس `::` ولا أي IPv6.
- رسائل iAP2 (0x4301 / مضيف 0x5703 إن وُجد) لا تتضمن IPv6.
- تُتجاهل عناوين IPv6 على واجهة الـ AP.
- لا يُستخدم تفضيل عائلة محفوظ ولا قلب العائلة بعد مهلة أول TCP على هذا المسار.
- السجلات تتضمن `family=IPv4 forced` و`hotspot interface selected iface=… ipv4=…`.

نسخة المحرّك عندنا (DiPlay 0.2.22) فيها أصلاً إصلاحا المنبع #394 (نشر IPv4 مع IPv6 على نقطة الاتصال) و#936 (عدم اختيار واجهات بيانات الجوال مثل `rmnet_data`). أضفنا حماية إضافية: حتى لو ظهرت `rmnet*` في قائمة الـ AP بالخطأ، يُختار `wlan0`/`softap`/`ap0` الذي يحمل IPv4 نقطة الاتصال.

الشبكة المشتركة (SAME_WIFI) لم تُغيَّر.

## 19. v1.6.6 (تجريبي): اختيار IPv4 أو IPv4 مع IPv6 تلقائياً على نقطة اتصال السيارة

1. قبل أي إعلان (Bonjour أو المستمعات أو رسالة 0x4301) يفحص CarLink واجهة نقطة الاتصال. يُعتبر IPv6 صالحاً فقط إذا وُجد عنوان عام (global/ULA) جاهز وغير مؤقت، يقبل الربط والاتصال المحلي، وIPv6 غير متوقف على الواجهة، ومسار IPv6 غير محلي موجود (إن أمكن قراءته). العنوان المحلي fe80 وحده لا يكفي أبداً، وهذا بالضبط ما في شاشة CS75.
2. إذا لم يكن IPv6 صالحاً بوضوح: نفس مسار v1.6.5 بالضبط، IPv4 فقط.
3. إذا كان صالحاً: IPv4 أولاً دائماً، ومعه IPv6 بمستمعات منفصلة (ليس مستمع :: واحد).
4. الرجوع التلقائي: إذا لم يفتح الآيفون اتصال AirPlay، أو فتحه وتم SETUP لكن الصورة لم تصل خلال 25 ثانية (التعليق القديم عند مرحلة الصورة)، تُحفظ هذه الشاشة على IPv4 فقط ويُعاد الاتصال فوراً بـ IPv4 فقط.
5. الحفظ لكل شاشة (بصمة من اسم الشبكة وواجهة نقطة الاتصال وطراز الجهاز) في مخزن خاص، ولا يُستخدم أبداً ما حُفظ من الشبكة المشتركة. تغيّر الشبكة يعني فحصاً جديداً، وحكم IPv4 فقط يُعاد فحصه بعد 30 يوماً أو بعد 3 فشل متتالية.
6. خيار شانجان CS75 Plus 2023 يبقى على IPv4 فقط مهما رأى الفحص. واجهات بيانات الجوال (`rmnet*` و`ccmni*`) ما زالت مستبعدة.
7. في شاشة التشخيص قسم «نوع عنوان IP (نقطة اتصال السيارة)»: المستخدم الآن، وهل تدعم الشاشة IPv6، والسبب، ووقت القرار.

## 30. زر «فتح إعدادات Android Auto» يظهر فقط إذا كانت الشاشة فيها Android Auto أصلي

تعليق المستخدم على v1.7.13: «فتح الاعدادات يطلع للي عنده الاصلي فقط». الزر في شاشات فشل خادم الوحدة الرئيسية (`HEAD_UNIT_SERVER_STUCK` و`HEAD_UNIT_SERVER_OFF`) كان يفتح تطبيق Android Auto على **الشاشة** (`com.google.android.projection.gearhead` / DefaultSettingsActivity، وإلا صفحة معلومات التطبيق). في CS75 Plus ما فيه Android Auto أصلي، فالزر بلا فائدة. والخادم اللي يحتاج Stop/Start هو على **الجوال**.

**تدقيق لكل ما يفترض وجود Android Auto أصلي على الشاشة:**

- **يُصلح:** زر «فتح إعدادات Android Auto» في الرئيسية (وإعدادات الفشل نفسها في معالج الإعداد إن ظهرت). يظهر فقط إذا `androidAutoInstalled && androidAutoCanRunCar` (`ConnectionPrefs.hasNativeAndroidAuto`). بدون ذلك يُخفى، ويبقى زر «إعادة المحاولة»، ويتغيّر نص الخطوات: العمل على الجوال (Stop ثم Start head unit server) ثم «إعادة المحاولة». نفس الاختيار في تقرير GitHub (`IssueReporter`).
- **كان صحيحاً وتُرك:** زر الرئيسية «تشغيل Android Auto على هذه الشاشة» يظهر فقط مع `offersAndroidAutoOnScreen` (المفتاح + التطبيق موجود ويقدر يشغّل وضع السيارة). مفتاح الإعدادات «Android Auto على هذه الشاشة» يظهر إذا التطبيق مثبّت، ويُعطَّل مع شرح إذا Google منع وضع السيارة (`aa_on_screen_unsupported`). نص الانتظار `server_waiting` ونص ورقة طريقة خادم الوحدة الرئيسية يقولان أصلاً «على الجوال». منطق الاتصال اللاسلكي ما يفتح تطبيق الشاشة. محرك Self Mode كان يفتح إعدادات Android Auto عند فشل الخادم المحلي، لكن CarLink يمنع ذلك (`onEngineEvent`) ويعرض الشاشة الخاصة به.
- لقطات المعرض: `failed-head-unit-server-stuck` و`-ar` بدون الزر (مثل هذه السيارة)، و`failed-head-unit-server-stuck-native` و`-native-ar` مع الزر لشاشات فيها Android Auto أصلي.

**ما كان يعمل أصلاً:**
- `WirelessServerRestartPolicy` مربوطة في `AapService.startWirelessServer()`: تفرّق بين «الخادم موجود في المتغير» و«المنفذ 5288 يستمع فعلاً»، وتعيد بناء خادم ميت مع تهدئة 10 ثوانٍ وحدّ 3 محاولات في 60 ثانية. تُستدعى عند `initWifiMode` لكل من الوضع 1 (طريقة خادم الوحدة الرئيسية) والوضع 3 (تلقائي / واي فاي مباشر / نفس الواي فاي / نقطة اتصال السيارة).
- `AaListenerRecoveryPolicy` مربوطة في `NativeAaHandshakeManager` (الوضع 3 فقط): تعيد فتح مستمعات Bluetooth إذا أسقطها راديو السيارة (#77). مسار الـ poke ومسار إعادة التسليح بعد الانقطاع (`rearmNativeAfterDrop`) كانا يعيدان التهيئة عند الحاجة.
- بعد انقطاع في الوضع 3 يُعاد `initWifiMode(force)` خلال 1.5 ثانية (أو إعادة اتصال سريعة على قناة Bluetooth إن فُعّلت). حلقة الاكتشاف في الوضع 1 كانت تُستأنف بعد ثانيتين.

**ما كان ناقصاً (على سيارة بلا Android Auto أصلي أيضاً):**
- `ACTION_START_WIRELESS` عندما المحرك مسلّح مسبقاً: `initWifiMode()` يخرج فوراً، فلا تُستدعى سياسة إعادة بناء 5288، ولا تُستأنف حلقة اكتشاف 5277 في الوضع 1 (الحلقة تتوقف أثناء الجلسة). مسار الـ poke يعالج المستمعات الضائعة، لكن طريقة خادم الوحدة الرئيسية لا تستخدم poke.
- بعد الانقطاع، `scheduleReconnectIfNeeded` كانت تعيد الاكتشاف فقط، بدون `startWirelessServer()`، فخادم 5288 الميت يبقى ميتاً في الوضع 1.
- إعادة المحاولة بعد خادم جوال عالق كانت بعد ثانيتين، فتتراكم مقابس على خادم لا يصلحه إلا الجوال.

**ما تغيّر:** عند بدء لاسلكي والمحرك مسلّح، تُصلح مستمعات السيارة (`rearmWirelessIfAlreadyArmed`: إعادة تهيئة إذا مستمعات Bluetooth ضائعة أو مغلقة للجلسة، وإلا `startWirelessServer()` + استئناف الاكتشاف في الوضع 1). بعد الانقطاع يُعاد بناء 5288 ثم الاكتشاف، والتأخير يتبع `UnresponsivePeerPolicy.reconnectDelayMs`: ثانيتان لانقطاع عادي، و10 أو 60 ثانية إذا الخادم على الجوال استقبل ولم يرد. رسالة «خادم الوحدة الرئيسية عالق» لم تتغير.

لا تغيير في واجهة المستخدم، ولا بناء APK في هذا الفرع.

## أفكار مؤجلة (Future ideas / postponed)

### `ConnectionAttempts`: حارس رقم الجيل لمحاولات الاتصال (قرار 28 نوفمبر 2026: لا نطبّقه الآن)

**الفكرة المقترحة:** كلاس على الخيط الرئيسي يعطي كل محاولة اتصال رقماً (جيلاً)، حتى لا يأثّر مؤقّت أو ردّ قديم من محاولة سابقة على جلسة جديدة.

- `begin(timeoutMs = 60s)`: يلغي المحاولة السابقة، ويعطي المحاولة `++lastId`، ويضع Runnable للمهلة لا يشتغل إلا إذا كان `activeId` لا يزال هو نفس الرقم.
- `connected(id)`: يمسح المهلة فقط إذا كان `id` هو الحالي.
- `cancel()`: يمسح المهلة.

**ملاحظات المراجعة:**
- `connected()` يرجع `true` أكثر من مرة لنفس الرقم؛ تُضاف `isCurrent(id)` للسؤال بدون أثر جانبي.
- استدعاء `cancel()` عند تدمير الخدمة أو الشاشة.
- إذا استُدعي الكلاس من خارج الخيط الرئيسي: استخدم `Job` + `delay` بدل `Handler`.

**سبب التأجيل:** سجل v1.7.11 أظهر خادم هاتف عالقاً وانقطاعات Wi-Fi، لا محاولات قديمة تتداخل مع جلسة جديدة، و`AaSessionTracker` عنده أصلاً مهلة 60 ثانية.

**متى نطبّقه:** فقط إذا أظهر سجل v1.7.12 (أو ما بعده) ردّاً (callback) قديماً من محاولة سابقة يؤثر على جلسة جديدة.

**تقييم 28 نوفمبر 2026 (سيارة بدون Android Auto أصلي):** راجع القسم 29. الفكرة ليست الحل لمشكلة الخادم العالق ولا لمهلة الـ 60 ثانية؛ `SessionManager` و`AndroidAutoAdapter` عندهم أصلاً حارس جيل (token + هوية المحاولة). لم تُنفَّذ.

**الكود** (لا يدخل المشروع الآن):

```kotlin
class ConnectionAttempts(
    private val onTimeout: (Long) -> Unit
) {
    private val handler = Handler(Looper.getMainLooper())
    private var lastId = 0L
    private var activeId: Long? = null
    private var timeout: Runnable? = null

    // تُستدعى كل الدوال على خيط الواجهة.
    fun begin(timeoutMs: Long = 60_000L): Long {
        cancel()
        val id = ++lastId
        activeId = id

        val task = Runnable {
            if (activeId == id) {
                cancel()
                onTimeout(id)
            }
        }
        timeout = task
        handler.postDelayed(task, timeoutMs)
        return id
    }

    fun connected(id: Long): Boolean {
        if (activeId != id) return false
        clearTimeout()
        return true
    }

    fun cancel() {
        activeId = null
        clearTimeout()
    }

    private fun clearTimeout() {
        timeout?.let { handler.removeCallbacks(it) }
        timeout = null
    }
}
```
